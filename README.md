# Airec

Самостоятельное приложение Python 3.10+ с русским Tkinter-интерфейсом.
Исходные проекты рядом не нужны. Облачной отправки и распознавания речи нет.

## Установка и запуск

Из корня рабочего пространства (на один уровень выше этого README):

```sh
cd airec
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e .
python -m airec
```

В текущем окружении editable-установка уже выполнена. Из корня рабочего пространства:

```sh
airec/.venv/bin/python -m airec
```

Готовый Linux-бинарник для x86_64 собирается GitHub Actions на Ubuntu 22.04.
Скачайте архив `airec-linux-x86_64` из раздела Artifacts запуска workflow,
распакуйте `airec` и запустите его. Для выполнения нужны системные Tk-библиотеки,
`pulseaudio-utils`, `xdg-utils` и PulseAudio либо PipeWire с PulseAudio-совместимым
сервером; AppIndicator/gdbus опциональны, при недоступности приложение работает
без иконки в трее. One-file бинарник предназначен для Ubuntu 22.04 и новее; на
других дистрибутивах совместимость зависит от версии glibc и библиотек Tk.

Готовый Windows-бинарник собирается GitHub Actions на `windows-latest`.
Скачайте `airec-windows-x86_64` из раздела Artifacts, распакуйте архив и запустите
`airec.exe`. Рядом приложен файл SHA-256 для проверки архива. Windows-сборка
предоставляет GUI и работу с существующими WAV, но запись аудио на Windows пока
не реализована.

Готовый macOS-бинарник для Apple Silicon собирается GitHub Actions на `macos-14`.
Скачайте архив `airec-macos-arm64` из раздела Artifacts, распакуйте его и запустите
`airec`. Бинарник не подписан и не нотариализован; macOS может потребовать разрешить
запуск в настройках безопасности. Запись аудио на macOS пока не реализована.

Linux Debian/Ubuntu для запуска из исходников: нужны `python3-tk`, `python3-venv`, `pulseaudio-utils`,
`xdg-utils`, PulseAudio либо PipeWire с PulseAudio-совместимым сервером.
Для трея дополнительно нужны `libglib2.0-bin` (gdbus), PyGObject и typelib
AppIndicator3 или AyatanaAppIndicator3, а также StatusNotifierHost рабочего стола.
Например, системные пакеты `python3-gi`, `gir1.2-ayatanaappindicator3-0.1`.
Имена пакетов зависят от дистрибутива. Чтобы системный PyGObject был виден в venv,
используйте системный Python и окружение с `--system-site-packages`, либо установите
PyGObject для выбранного интерпретатора. Для pyenv-Python системный пакет может
быть несовместим; приложение всё равно работает без трея.

Windows PowerShell, из этого каталога:

```powershell
py -3 -m venv .venv
.venv\Scripts\python -m pip install -e .
.venv\Scripts\python -m airec
```

На macOS используются те же команды, что на Linux; Python должен включать Tk.
На Windows/macOS запись честно сообщает «Запись на этой ОС пока не реализована».
GUI, настройки и операции с существующими WAV не требуют pactl/parec.

## Поведение

- «Начать запись» включает наблюдение, а не немедленный захват. Без внешних
  потребителей выбранного микрофона аудиофайл не создаётся.
- При появлении потребителя запускается parec; собственный поток исключается
  по PID и уникальному свойству. Статус записи появляется после обнаружения
  собственного потока в аудиосервере, а не просто создания процесса.
- После исчезновения внешних потребителей WAV закрывается, наблюдение продолжается.
  Следующая активность создаёт новый файл. Повторное нажатие останавливает наблюдение.
- Используется системный микрофон по умолчанию. При изменении имени или индекса,
  исчезновении устройства, выборе monitor-источника или сбое сервера наблюдение
  завершается с ошибкой. Нужно выбрать микрофон и запустить наблюдение заново.
- Записывается только микрофон, не системный звук и не гарантированно обе стороны звонка.
- Флажок запуска выключен по умолчанию; изменение сохраняется, но не меняет
  текущий сеанс. Это не автозагрузка ОС.
- Закрытие главного окна скрывает его только при подтверждённом запуске трея.
  Без трея окно остаётся доступным. «Выход» есть и в окне, и в трее.
- На Linux поддерживается AppIndicator/StatusNotifier, а не legacy XEmbed.
  Проверяется зарегистрированный host; ошибки импорта и запуска дают fallback.
  На Windows pystray работает в отдельном потоке. На macOS трей намеренно
  отключён: Cocoa требует главного потока, надёжная интеграция с Tk здесь не реализована.
  Работу иконки в конкретном desktop необходимо проверить вручную; исчезновение
  самого host после успешного запуска не отслеживается отдельным D-Bus watcher.
- Одно корневое окно, список записей — переиспользуемый Toplevel.
  Импорт копирует WAV, не меняя оригинал; повторный импорт управляемого файла
  не дублирует его. Прослушивание использует системную ассоциацию WAV.
  Удаление требует подтверждения. Символические ссылки не удаляются.
- Пауза, расшифровка, участники и саммари явно недоступны.

## Файлы и настройки

При запуске из исходников записи находятся в `recordings` внутри этого проекта,
то есть `airec/recordings` относительно исходного рабочего пространства. У
собранного бинарника они сохраняются в пользовательском каталоге данных платформы,
вне временного каталога распаковки one-file. Worker, импорт и GUI используют один путь.
Настройки и логи находятся в пользовательских каталогах platformdirs.

Активные и аварийные файлы имеют расширение `.partial`. Только после штатной
остановки parec и проверки PCM WAV файл переименовывается в `.wav`. Незавершённые
файлы отображаются, но прослушивание, импорт и удаление через GUI заблокированы.
После аварии их можно исследовать вручную, предварительно завершив приложение.
Файлы не ремонтируются автоматически и не выдаются за успешные записи.
Импорт поддерживает PCM WAV, распознаваемый стандартным модулем wave; сжатый WAV
может быть отклонён. Валидация читает данные порциями в фоновом потоке.

Настройки и ротируемые логи находятся в platformdirs-каталогах **Airec**;
точные пути видны через «Настройки…». Типичные Linux-пути:
`~/.config/Airec/settings.json`, `~/.local/state/Airec/log`.
Логи application и worker: по 1 МБ, три резервные копии каждого.
Настройки имеют версию схемы, валидацию и атомарное сохранение. Повреждённый
файл не перезаписывается: приложение сообщает путь; исправьте или перенесите
его вручную. Активность записи не сохраняется как настройка.

## Архитектура и остановка

`ui` → `controller` → `service` → отдельный `worker` → `backends/linux` → parec.
JSON-lines IPC версии 1 передаёт ready, waiting, recording_started,
recording_finished, error и exited; stdout не используется для логов.
GUI принимает события через очереди, операции диска выполняет отдельный executor.
Процесс имеет отдельную POSIX-сессию; супервизор контролирует также оставшиеся
процессы захвата после аварии worker. Сигналы отправляются через psutil с
проверкой идентичности процесса. Межпроцессная блокировка portalocker исключает
второй экземпляр для одного пользовательского каталога настроек. Не используйте
разные XDG_CONFIG_HOME для обхода блокировки параллельных экземпляров.

Handshake worker: 12 секунд; команды pactl: 3 секунды; подключение захвата:
5 секунд. Остановка аудио: SIGINT/4 секунды, TERM/1, KILL/1.
Супервизор: команда stop/12 секунд, TERM/2, KILL/2. При отказе ОС завершить
процессы владение сохраняется, повторный запуск запрещён, доступна повторная
остановка. EOF управляющего канала останавливает worker и захват.
Неограниченного блокирующего ожидания процесса в GUI нет. Зависшая файловая
система всё же может задержать фоновые операции и выход; аппаратные/сетевые
зависания диска не имеют переносимого Python-таймаута.

## Проверки

Из каталога этого README:

```sh
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python tests/gui_smoke.py
.venv/bin/python -m compileall -q airec tests
.venv/bin/python -m pip check
```

Автотесты не записывают реальный микрофон. Модульные тесты подменяют аудиобэкенд;
интеграционные тесты запускают синтетические Python-процессы для реального IPC,
таймаутов, блокировки экземпляров и завершения дерева. GUI smoke требует дисплея,
использует подменённые сервис и трей, проверяет окна, fallback, очередь команд,
настройки и асинхронный выход; это не тест реальной иконки.

Фактически выполнено на Linux/Python 3.10.19:

- 28 тестов успешно; GUI smoke успешно на доступном дисплее.
- Editable-установка, compileall и pip check успешны.
- Проверены справка parec 16.1 и список форматов: используется позиционный путь
  с `--file-format=wav`, не несуществующий `--file=...`.
- pactl info подтвердил PulseAudio-совместимый сервер PipeWire 1.6.0.
- StatusNotifierHost обнаружен, но реальный запуск трея дал fallback из-за
  отсутствия `gi` в venv. Успешная работа реальной иконки не проверена.
- Контрольные суммы исходных gui, recorder и appark остались неизменными.

Реальный захват/качество звука, запуск внешнего плеера, Windows и macOS не проверены.
Наличие аудиосервера и mock-тесты не являются проверкой реального аудио.

### Ручной сценарий Linux (записывает микрофон)

1. Запустить приложение, включить наблюдение без внешних потребителей: должно
   быть «Ожидание звонка», без нового аудиофайла.
2. Осознанно открыть микрофон в тестовом приложении, произнести тестовую фразу:
   дождаться «Идёт запись». Закрыть потребителя, дождаться завершённого WAV.
3. Прослушать WAV системным плеером, проверить реальный звук и длительность.
4. Повторить активность, проверить новый файл, остановку во время записи,
   закрытие/возврат через настоящий трей и полный выход без оставшихся процессов.
5. Проверить отказ прав каталога, смену микрофона и исчезновение аудиосервера.

Этот ручной аудиосценарий при реализации не выполнялся.
